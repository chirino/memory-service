Memory Service can export durable lifecycle events and current-state records to an analytics database. The processor runs outside the request path, so an analytics outage does not delay application writes.

ClickHouse is the supported analytics provider. The processor reads the admin durable event stream, fetches bounded source records, writes batches to ClickHouse, and saves its safe cursor through `AdminCheckpointService`.

## Choose what to export

The payload mode controls which source data crosses into the analytics system.

| Mode        | Data written                                                                           | Use it for                        |
| ----------- | -------------------------------------------------------------------------------------- | --------------------------------- |
| `metadata`  | Resource identities, timestamps, routing fields, and allowlisted conversation metadata | Operational dashboards            |
| `projected` | Metadata plus entry content and memory values/attributes available to Rego             | Approved domain fields            |
| `full`      | Also makes conversation title and entry indexed content available to Rego              | Explicit full-content projections |

Every application table is a projection. Without projection paths, the processor loads packaged metadata-only manifests for `conversations`, `entries`, and `memories`. These defaults store no titles, content, memory values, or arbitrary JSON. Explicit paths replace that entire set. Even in full mode, only columns selected by a manifest are persisted; full mode requires `--allow-decrypted-content`.

The default `conversations` projection declares exactly `created_at`, `updated_at`, and `archived`, in addition to processor-owned identity and bookkeeping columns. Owner, client, agent, and fork/started-by IDs remain available in `input.record` for [opt-in conversation reporting](/docs/analytics/projections/#add-conversation-reporting-fields).

## Understand the exported data

Conversations, entries, and memories use the same [projection pipeline](projections/). Opt-in conversation projections can expose fork and started-by relationships as typed columns. There is no generic payload copy or separate lineage table.

Each projection creates a physical table and two views. `<table>_all` selects the latest snapshot, including a tombstone. `<table>_current` excludes deleted resources and conversation groups. Multi-row projections return the rows of the latest snapshot. Use current views for dashboards; physical tables retain older versions until TTL or purge removes them.

`lifecycle_events_current` contains durable lifecycle observations. Opt-in `--export-memberships` populates the fixed `conversation_memberships_current` relation for group-access reports. Membership analytics are eventually consistent; applications must still check access against live Memory Service.

## Keep the trust boundary explicit

ClickHouse is a separate persistence boundary. Configure its storage, replicas, backups, caches, temporary files, and disaster-recovery copies to meet the same deletion and encryption requirements as Memory Service.

The processor stores Memory Service source identifiers in ClickHouse so analytics results can link back to authoritative records through the Memory Service API. Grant ClickHouse access accordingly. Payload modes and projection manifests control which source fields accompany those identifiers.

Continue with the [ClickHouse quickstart](/docs/analytics/clickhouse/).
