The processor serves `/healthz`, `/readyz`, and `/metrics` on port `8081`. Readiness means it owns the checkpoint lease and has an active subscription. It does not prove that all source events have reached ClickHouse. Keep one active owner per client ID; Kubernetes deployments use `Recreate`.

## Understand startup and recovery

A fresh exporter captures a durable source boundary, scans current conversations, entries, and memories, then replays the outbox from that boundary before entering live delivery. Membership scans are included when enabled. Bootstrap and live events use the same normalization and projection pipeline.

A restarted snapshot scan starts at the beginning while retaining its original catch-up boundary. Current-state rows replace earlier observations. The checkpoint commits the requested projection configuration and replay ID only after catch-up reaches live delivery. Keep outbox retention longer than the longest outage plus scan duration. A cursor outside retained history stops the exporter with `backfill_required`; it never skips the missing interval.

On PostgreSQL, monitor `memory_service_outbox_unsequenced_oldest_age_seconds` if application writes continue but delivery stops. See [Outbox relay metrics](/docs/configuration/#outbox-relay-metrics).

## Manage schemas

`--schema-mode=manage` claims an empty dedicated database with the current fingerprint and creates owned objects. Matching interrupted infrastructure initialization can finish on restart, including a crash that left only the exact current empty schema registry before its checksum was stored. `validate` checks the current schema without DDL. Neither mode adopts an older or unowned nonempty database.

The registry stores the schema checksum and application time. It has no numeric schema version. Projection registration requires explicit row mode and ordering. The processor rejects conflicting manifests, physical types, keys, engines, partitioning, missing registry metadata, and orphan user relations. It never infers an old layout or drops an orphan automatically.

A projection chain can add nullable columns through manage mode. Validate mode reports the required `ALTER TABLE` statements; run manage once to register the extension and recreate its views, then return to validate. Registered manifests stay immutable. A whole configured-out table remains registered for cleanup and retention.

```sql
SELECT table_name, projection_name, previous, row_mode, ordering, projection_digest
FROM memory_service_analytics.projection_registry FINAL
ORDER BY table_name, projection_name;
```

## Cut over an existing analytics installation

If the previous exporter was running, rebuild its analytics dataset in a separate database. The new exporter cannot resume its checkpoint or upgrade its ClickHouse tables in place. Both `manage` and `validate` reject the old schema. Changing `--projection-replay-id` does not convert it.

This cutover changes only analytics. Keep the operational PostgreSQL, SQLite, or MongoDB datastore, attachments, source outbox, and other processors' checkpoints. Do not reset Memory Service or delete its storage volumes.

### Prepare and stop the previous exporter

1. Save the old binary or image reference, exporter configuration, database name, client/exporter IDs, and reader configuration. Preserve access to its checkpoint for rollback.
2. Finish pending deletion work using the old exporter or its cleanup owner. Stop the old exporter and let outstanding ClickHouse requests finish. The new exporter does not process the old database's purge queue.
3. Decide which old analytics history must be retained. The rebuild scans current source records and catches up through the outbox. It does not copy old ClickHouse rows or recreate lifecycle history, intermediate revisions, or source records that are no longer retained.

An old dataset kept for history or rollback still needs its existing retention and deletion procedures while Memory Service continues to receive changes. Keep those responsibilities assigned until the dataset, its backups, and its readers are retired.

### Prepare the new configuration

Translate custom projections to `input.record` and declare `projectionRego` on each root. Remove `--generic-payload-retention` and its environment variable, remove `conversations:lineage` disable selectors, and change an explicit `continue-generic` failure policy to `record`. Projected and full modes no longer write an automatic generic JSON copy. See [projection manifests](/docs/analytics/projections/) and the [configuration reference](/docs/analytics/clickhouse/configuration/).

With no projection paths, the packaged defaults create `conversations`, `entries`, and `memories`. The conversation table has only `created_at`, `updated_at`, and `archived`, plus processor-owned columns. Owner, client, agent, and lineage fields need the [opt-in conversation details projection](/docs/analytics/projections/#add-conversation-reporting-fields). Explicit paths replace the entire packaged set. Update dashboards that used generic payload columns or the dedicated lineage table.

Provision an empty, dedicated ClickHouse database and grant the analytics user access to it, including the [schema and server-settings permissions](/docs/analytics/clickhouse/configuration/#clickhouse-connection). If you reuse a ClickHouse server or volume, apply the new database and grants explicitly; changing the repository's initialization SQL alone is not a cutover procedure. Leave the old database intact. The bundled `task kind:deploy` reapplies these grants even when ClickHouse retains an existing data volume. If you apply the local kind overlay manually, run `task kind:clickhouse:provision` afterward.

The repository's `deploy/clickhouse/init.sql` is fixed to `memory_service_analytics`. For another database name, run these statements as a ClickHouse administrator, replacing `analytics_rebuild` and `memory_service_analytics` with your database and analytics user:

```sql
CREATE DATABASE IF NOT EXISTS analytics_rebuild;
GRANT CREATE DATABASE, CREATE TABLE, DROP TABLE, CREATE VIEW, DROP VIEW, SELECT, INSERT, ALTER ON analytics_rebuild.* TO memory_service_analytics;
GRANT SELECT ON system.merge_tree_settings TO memory_service_analytics;
```

Choose a new Memory Service client ID with the `admin` role and matching credentials. This ID owns a fresh checkpoint. Also choose a fresh exporter ID, which namespaces ClickHouse rows. For example, these settings name a new dataset; substitute names that have never been used in your deployment:

```bash
export MEMORY_SERVICE_PROCESS_CLIENT_ID=analytics-rebuild
export MEMORY_SERVICE_CLICKHOUSE_EXPORTER_ID=analytics-rebuild
export MEMORY_SERVICE_CLICKHOUSE_DATABASE=analytics_rebuild
export MEMORY_SERVICE_CLICKHOUSE_SCHEMA_MODE=manage
export MEMORY_SERVICE_CLICKHOUSE_PAYLOAD_MODE=metadata
export MEMORY_SERVICE_PROCESS_AFTER_CURSOR=start
```

Keep the connection, TLS, authentication, and retention settings appropriate for your deployment. Replace the old API key with credentials for the new client. Do not copy or overwrite the previous checkpoint. Leave `--tail-only-development` off so the new dataset receives a current-state scan. A fresh dataset needs no projection replay ID.

The exporter refuses to start when its client ID holds a checkpoint from the previous exporter, and when the dataset already holds rows from the current or a later checkpoint lease, which happens after a checkpoint is lost or deleted. Both errors ask for a new client ID and a new empty database. Rebuild the dataset rather than reusing the old identities.

### Bootstrap, verify, and switch readers

Start the new exporter. It initializes the empty database, scans retained current state, and catches up before entering live delivery. Keep outbox history available for the full scan and catch-up period.

Read the new client's checkpoint with `GET /v1/admin/checkpoints/analytics-rebuild` using that client's admin credentials. The processor-defined `value.bootstrap.state` must reach `complete`. Readiness alone is insufficient because it reports lease ownership and subscription health. `value.lastEventCursor` is already set when the scan starts, to the outbox cursor where it began (`start` on an empty outbox), so a nonempty value does not show live delivery. The test record change below does.

Before switching readers:

- Check the expected projection tables and sample current rows, scoped to the new exporter ID. Compare retained source records with their projected rows; historical event counts need not match the old dataset.
- Inspect `projection_failures` and resolve unexpected failures. A running exporter with failure policy `record` can still omit failed projection rows.
- Create or update a test source record and confirm its current row changes. Delete it and confirm the row disappears from the current view. If memberships are enabled, verify a grant and revoke too.
- Point dashboards and applications at the new database and typed columns. Keep queries scoped by exporter ID.

Retire the old dataset only after readers have switched and its history, retention, deletion, and rollback obligations are resolved. Upgrading a binary never resets either dataset.

### Roll back as one deployment

Stop the new exporter and restore the old binary, configuration, database, checkpoint identity, and readers together. Never point the old binary at the new database or the new binary at the old database. The old exporter can catch up only while its saved cursor remains within retained source history. If it has expired, restoring the binary alone cannot recover the missing interval.

## Retain analytics data

Active projection and membership rows use `--projection-retention`; deleted rows use `--tombstone-retention`, both measured on `observed_at`. Positive tombstone retention requires positive active retention no longer than the tombstone retention. Lifecycle and failure retention have separate controls. Zero means no TTL.

Deletion fences have no automatic TTL. Retire them only after the dataset's writers and resumable checkpoints are retired. They retain identities, without application content.

Live exporters sharing a database must agree on managed retention values. Heartbeats and the write path renew ownership; loss of ownership stops writes. In `external` retention mode, the operator owns TTLs and the exporter neither validates nor changes them.

## Process deletions

Managed purge writes the complete typed scope and ingestion cutoff into `purge_queue`, writes identity/group fences, removes matching rows, waits for mutations, and records `complete` before checkpoint advancement. Cleanup uses exact kind/ID or canonical group UUID, always scoped by exporter. Membership revokes also use the stored cutoff to preserve later grants; purges for retired resource IDs and groups remove every matching version, including rows replayed under a new lease. Transient purge lookups retry without advancing the checkpoint; a conflicting stored scope stops the exporter. Cleanup needs no resource catalog. Replayed deletes reuse the original cutoff so an older revoke cannot erase a newer grant.

Record-only mode persists pending work for an external worker. External mode writes no queue request and delegates physical cleanup. Disabled outputs still receive cleanup notifications in managed and record-only modes. With membership export off, a revoke writes no fence and queues no purge unless an earlier enabled run left rows for that membership, so removed users' IDs are not retained. Rows from an earlier enabled run are still purged.

```sql
SELECT purge_id, resource_kind, analytics_resource_id, conversation_group_id,
       purge_scope, cutoff_ingest_version, status, requested_at
FROM memory_service_analytics.purge_queue FINAL
WHERE status = 'pending'
ORDER BY requested_at;
```

A complete purge acknowledges its submitted mutations. Fences hide an older row inserted after cleanup, but do not physically remove a future INSERT. Retention and external cleanup procedures must account for outstanding requests during exporter takeover, along with replicas, backups, caches, and disaster-recovery copies.

## Replay projections or enable memberships

Set a fresh `--projection-replay-id` when adding a projection, re-enabling an output, or requesting recomputation with a chain's replacement logic. The scan includes current conversations, entries, memories, and enabled memberships. No user projection paths are required to replay the packaged defaults.

```bash
memory-service process clickhouse \
  --endpoint memory-service:8080 \
  --client-id primary-analytics \
  --api-key "$MEMORY_SERVICE_ANALYTICS_API_KEY" \
  --clickhouse-address clickhouse.example:9440 --clickhouse-tls \
  --clickhouse-database memory_service_analytics \
  --clickhouse-username memory_service_analytics \
  --clickhouse-password-file /run/secrets/clickhouse-password \
  --export-memberships --projection-replay-id enable-memberships
```

An enabled membership exporter first checks `features.analytics_membership_snapshots`. Unsupported sources fail before bootstrap. Reusing the same replay ID requests no new scan. Resume a pending replay with its exact original configuration and ID. Removing a projection or disabling output does not trigger a scan or create replacement capture.

## Diagnose projection failures

The default `record` policy writes payload-free diagnostics to `projection_failures` and continues. `stop` halts on Rego or output validation errors. A missing source snapshot is recorded and skipped under both policies so normal catch-up can reach its later deletion event. Failures include typed resource identities and ingestion versions. Compare error codes with the source shape and declared columns; source payloads are never stored in diagnostics.
