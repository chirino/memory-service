Java applications can run Memory Service as an owned subprocess without requiring a separate
installation. The process API downloads and caches the native executable on first use, starts a
local SQLite service over a protected Unix domain socket, waits for readiness when it can discover the management endpoint,
and stops the child when closed.

This integration is subprocess-based, not JNI. It currently supports Linux AMD64, Linux ARM64, and
macOS ARM64. Windows and Intel macOS are not packaged.

## Add the dependency

Depend on `memory-service-process`. It contains the process API and, for every supported platform,
a small descriptor that names the executable's OCI artifact and digests:

<Code
  lang="xml"
  code={`<dependency>
  <groupId>io.github.chirino.memory-service</groupId>
  <artifactId>memory-service-process</artifactId>
  <version>${PROJECT_VERSION}</version>
</dependency>`}
/>

Releases before 0.6.0 shipped the executables in `memory-service-binaries` and the
`memory-service-binary-<platform>` JARs. Those artifact IDs are now relocation POMs that resolve to
`memory-service-process`, so existing declarations keep working and Maven prints a warning asking
you to depend on `memory-service-process` directly.

The first `start()` on a machine downloads the executable for the current platform from
`ghcr.io/chirino/memory-service-binary`, verifies it against the digests in the signed JAR, and
caches it. Later starts use the cache without any network access. See
[Download the executable](#download-the-executable) for mirrors, credentials, and offline use.

## Start a local service

```java
import io.github.chirino.memoryservice.process.MemoryServiceProcess;
import java.nio.file.Path;

Path stateDirectory = Path.of(System.getProperty("user.home"), ".my-app", "memory");

try (MemoryServiceProcess service = MemoryServiceProcess.builder(stateDirectory).start()) {
    String target = service.target(); // unix:///.../memory.sock
    // Configure your Memory Service client with target.
}
```

The builder creates `memory.db` and `memory.sock` below the state directory. It configures SQLite,
local Unix-socket authentication, no embedding provider, and plain local encryption. These defaults
are intended for a single-user local process, not a remote production deployment.

The child command is only `memory-service serve`. Server configuration is supplied through
`MEMORY_SERVICE_*` environment variables, using the same configuration surface as container
deployments:

| Default environment variable                 | Value                           |
| -------------------------------------------- | ------------------------------- |
| `MEMORY_SERVICE_PLAIN_TEXT`                  | `true`                          |
| `MEMORY_SERVICE_TLS`                         | `false`                         |
| `MEMORY_SERVICE_DB_KIND`                     | `sqlite`                        |
| `MEMORY_SERVICE_DB_URL`                      | `<state-directory>/memory.db`   |
| `MEMORY_SERVICE_UNIX_SOCKET`                 | `<state-directory>/memory.sock` |
| `MEMORY_SERVICE_UNIX_SOCKET_AUTH`            | `local`                         |
| `MEMORY_SERVICE_EMBEDDING_KIND`              | `none`                          |
| `MEMORY_SERVICE_ENCRYPTION_ALLOW_PLAIN`      | `true`                          |
| `MEMORY_SERVICE_MANAGEMENT_ON_MAIN_LISTENER` | `true`                          |

Startup normally returns only after `GET /ready` succeeds. A startup timeout or early child exit
throws `MemoryServiceStartException` with recent child output. `close()` is idempotent and first
requests a graceful stop, then forcibly terminates a child that exceeds the shutdown timeout.

## Configure the server

Builder environment entries override the local defaults, so any `serve` option with a
`MEMORY_SERVICE_*` equivalent can be configured without changing the child command:

```java
import java.util.Map;

MemoryServiceProcess process = MemoryServiceProcess.builder(stateDirectory)
    .environment(Map.of(
        "MEMORY_SERVICE_EMBEDDING_KIND", "local",
        "MEMORY_SERVICE_VECTOR_KIND", "sqlite"))
    .start();
```

`databasePath(Path)` and `socketPath(Path)` are typed conveniences that configure
`MEMORY_SERVICE_DB_URL` and `MEMORY_SERVICE_UNIX_SOCKET`. The effective listener environment
controls `target()` and readiness probing, so changing listeners through the typed methods or
`environment(...)` remains consistent.

### Use an HTTP listener

Call `httpListener(...)` to disable the default Unix socket and select a plaintext HTTP listener.
TCP access does not use local Unix-socket identity, so configure the server's normal API-key or OIDC
authentication as well:

```java
MemoryServiceProcess process = MemoryServiceProcess.builder(stateDirectory)
    .httpListener("127.0.0.1", 8082)
    .environment("MEMORY_SERVICE_API_KEYS_MY_APP", apiKey)
    .start();

String target = process.target(); // http://127.0.0.1:8082
```

`httpListener(int)` uses `127.0.0.1`. `disableUnixSocket()` only removes the managed-process Unix
socket settings and leaves the final HTTP host, port, plaintext, and TLS values to the server
configuration. For a non-loopback plaintext host, explicitly set
`MEMORY_SERVICE_ALLOW_NON_LOOPBACK_PLAINTEXT=true`.

`unixSocketPath()` returns an `Optional<Path>` for code that supports either transport. The older
`socketPath()` convenience throws `IllegalStateException` when HTTP is selected.

### Configure readiness

The process API chooses its readiness checker from the final child environment after defaults,
inherited values, removals, and explicit overrides have all been applied:

- With `MEMORY_SERVICE_MANAGEMENT_ON_MAIN_LISTENER=true`, it probes the selected main Unix-socket or
  HTTP listener.
- A configured `MEMORY_SERVICE_MANAGEMENT_UNIX_SOCKET` or explicit
  `MEMORY_SERVICE_MANAGEMENT_PORT` selects that dedicated management listener.
- `managementHttpListener(...)` configures a dedicated plaintext management HTTP listener and
  disables management on the main listener.
- If management is not on the main listener and neither a management Unix socket nor an explicit,
  usable management port is configured, no readiness address is knowable. `start()` launches the
  child and returns without waiting. The server can still exit later if its own configuration is
  invalid.

For example, the following probes readiness on port 9090 while clients connect on port 8082:

```java
MemoryServiceProcess process = MemoryServiceProcess.builder(stateDirectory)
    .httpListener(8082)
    .managementHttpListener(9090)
    .environment("MEMORY_SERVICE_API_KEYS_MY_APP", apiKey)
    .start();
```

The builder normally removes inherited `MEMORY_SERVICE_*` entries before applying its defaults,
which prevents the parent shell from unexpectedly changing the managed child. Use
`inheritMemoryServiceEnvironment(true)` to let inherited entries replace defaults. Explicit
`environment(...)` entries always have the highest precedence. Unrelated inherited variables such
as `PATH` and `HOME` are retained. `removeEnvironment(name)` removes either an inherited or default
entry; a later `environment(name, value)` restores it.

## Route process output

By default, stdout and stderr are merged into one bridge and sent to Java util logging at `FINE`.
Supply consumers to integrate with application logging:

```java
import java.util.function.Consumer;

Consumer<String> output = line -> applicationLogger.info(line);

MemoryServiceProcess process = MemoryServiceProcess.builder(stateDirectory)
    .standardOutput(output)
    .standardError(output)
    .start();
```

When both methods receive the same non-null consumer instance, stderr is merged into stdout and one
bridge thread is used. Passing `null` to either method redirects that stream to the operating
system's null device; passing `null` to both creates no bridge threads.

## Control binary resolution

Packaged resolution is the default. You can replace it with an ordered resolver list:

```java
import io.github.chirino.memoryservice.process.MemoryServiceBinary;

MemoryServiceProcess process = MemoryServiceProcess.builder(stateDirectory)
    .binaryResolvers(
        MemoryServiceBinary.file(Path.of("/opt/my-app/memory-service")),
        MemoryServiceBinary.packaged(),
        MemoryServiceBinary.onPath("memory-service"))
    .start();
```

A resolver falls through only when its source is unavailable. If a candidate exists but is corrupt,
cannot be extracted, or cannot be launched, startup fails instead of silently selecting a different
binary.

Packaged executables are checksum-verified and cached by platform and SHA-256. The default cache is
`~/.cache/memory-service/binaries` on Linux and
`~/Library/Caches/memory-service/binaries` on macOS. Use `cacheDirectory(Path)` to override it.

The builder also provides typed configuration for startup and shutdown timeouts, the packaged
binary cache, binary resolution, output consumers, and the JVM shutdown hook.

## Download the executable

The packaged resolver fetches one gzip layer by digest over the standard OCI distribution API and
checks both the layer digest and the executable's SHA-256 before caching it. The digests come from
the native JAR, so a registry, mirror, or proxy can't substitute different content. Concurrent
starts in one JVM or across processes download once. The download happens before the process
launches, so `startupTimeout` does not include it. Progress is logged through Java util logging
under `io.github.chirino.memoryservice.process.OciBlobFetcher`.

The artifact is public, so no credentials are needed. When `GH_TOKEN` or `GITHUB_TOKEN` is set, it
is used for `ghcr.io` only, which helps when GitHub throttles anonymous pulls. A token that GHCR
rejects is ignored with a warning. GitHub Actions does not export the workflow token to steps by
default; add it to the job's environment to use it:

```yaml
env:
  GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

### Configure registries in code

Pass `MemoryServiceBinaryRegistries` to `MemoryServiceBinary.packaged(...)` to use mirrors,
credentials, an internal CA, a proxy, or another timeout. These settings exist only in code: no
environment variable or system property can add a mirror or redirect credentials.

```java
import io.github.chirino.memoryservice.process.MemoryServiceBinary;
import io.github.chirino.memoryservice.process.MemoryServiceBinaryRegistries;

MemoryServiceBinaryRegistries registries = MemoryServiceBinaryRegistries.builder()
    .mirror("ghcr.io", "harbor.corp.example/ghcr-proxy")
    .credentials("harbor.corp.example", "robot$memory-service", harborToken)
    .trustedCertificates(Path.of("/etc/pki/tls/certs/corp-ca.pem"))
    .githubTokenFromEnvironment(false)
    .build();

MemoryServiceProcess process = MemoryServiceProcess.builder(stateDirectory)
    .binaryResolvers(MemoryServiceBinary.packaged(registries))
    .start();
```

| Builder method                        | Purpose                                                                 | Default                       |
| ------------------------------------- | ----------------------------------------------------------------------- | ----------------------------- |
| `mirror(prefix, location)`            | Map a repository prefix to a mirror. Repeat to add more, tried in order | none                          |
| `upstreamFallback(boolean)`           | Try `ghcr.io` after every mirror fails                                  | `false` when a mirror matches |
| `credentials(host, username, secret)` | Credentials for one registry host                                       | none                          |
| `githubTokenFromEnvironment(boolean)` | Use `GH_TOKEN`, then `GITHUB_TOKEN`, for `ghcr.io`                      | `true`                        |
| `trustedCertificates(Path)`           | Trust extra CA certificates from a PEM file, in addition to the JVM's   | none                          |
| `proxy(ProxySelector)`                | Proxy selection for registry requests                                   | `ProxySelector.getDefault()`  |
| `downloadTimeout(Duration)`           | Deadline for one registry location, including retries                   | 5 minutes                     |

Mirror rules follow the `prefix` and `location` model from containers' `registries.conf`. The
longest matching prefix wins, and the rest of the repository path is appended to the location, so
`mirror("ghcr.io", "harbor.corp.example/ghcr-proxy")` resolves
`ghcr.io/chirino/memory-service-binary` to
`harbor.corp.example/ghcr-proxy/chirino/memory-service-binary`. Locations use HTTPS unless they
start with `http://`. Once a mirror matches, `ghcr.io` is contacted only if you enable
`upstreamFallback(true)`, which keeps air-gapped hosts from reaching out.

Credentials belong to one host. They are sent only to that host over HTTPS and to the token realm it
names, never to a mirror on another host and never over `http://`. Registries that accept a bare
token, such as GHCR, take any username: `credentials("ghcr.io", "token", githubToken)`. The library
does not read Docker or containers auth files; parse them yourself and call `credentials(...)` if
you want to reuse a `docker login`.

Each location gets up to three attempts for connection failures, `5xx`, and `429` responses. When a
mirror returns `404`, the resolver pulls the release manifest once so pull-through caches such as
Harbor, Artifactory, and Nexus can populate, then retries. If every location fails, startup fails
with an error that lists each location and why.

Without `proxy(...)`, the JVM's standard `https.proxyHost`, `https.proxyPort`, and
`http.nonProxyHosts` system properties apply. `HTTPS_PROXY` and `NO_PROXY` are not read.

### Populate a mirror

A pull-through cache needs only a project or remote repository that points at `ghcr.io`. For a
disconnected registry, copy each release across the air gap with standard tools:

<Code
  lang="bash"
  code={`# Connected side
oras copy --to-oci-layout ghcr.io/chirino/memory-service-binary:${PROJECT_VERSION} ./memory-service-binary:${PROJECT_VERSION}
# Disconnected side
oras copy --from-oci-layout ./memory-service-binary:${PROJECT_VERSION} \\
  harbor.corp.example/ghcr-proxy/chirino/memory-service-binary:${PROJECT_VERSION}`}
/>

`skopeo copy` works the same way.

### Run without registry access

Hosts that can't reach any registry can use `MemoryServiceBinary.file(...)` or `onPath(...)` with an
executable from the GitHub Release ZIPs. You can also fill the cache on a connected machine and ship
the cache directory, for example in a container image layer, then point `cacheDirectory(Path)` at
it:

```java
MemoryServiceBinary.resolve(List.of(MemoryServiceBinary.packaged(registries)), cacheDirectory);
```

The cache layout is `<cacheDirectory>/<platform>/<sha256>/memory-service`. Executables in the cache
are verified again on every start.

## Executable JARs and shading

The descriptors live under `META-INF/memory-service/` in `memory-service-process`. Fat-JAR tools
copy them by default, so no extra configuration is needed.

If you supply your own `MemoryServiceBinaryProvider`, for example a JAR that embeds an executable
for offline use, it is discovered with Java `ServiceLoader` and takes precedence over the bundled
descriptor. When you build an uber-JAR with Maven Shade, merge service descriptors so its
registration is retained:

```xml
<transformer implementation="org.apache.maven.plugins.shade.resource.ServicesResourceTransformer" />
```
