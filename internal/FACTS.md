# Internal Module Facts

**urfave slice destinations**: urfave/cli v3 `StringSliceFlag` replaces a nil `Destination` slice with an empty slice even when the flag is unset. Defaults consumed after CLI parsing must treat both nil and empty slices as unset, or provide an explicit flag value.
**BDD hardened config**: BDD server runners must start from `defaultBDDConfig()`, which selects the `dek` provider, supplies the fixed test key, and explicitly serves management routes on the ephemeral main listener. `config.DefaultConfig()` leaves `plain` primary and management placement undecided; production-mode runners require explicit unsafe opt-ins for both. Use `dek` when the suite must exercise MSEH v4 field encryption.
**Plain encryption behavior**: `MEMORY_SERVICE_ENCRYPTION_ALLOW_PLAIN=true` only acknowledges the unsafe production configuration. The encryption service passes byte, field, and stream operations through unchanged when `plain` is primary, so database fields and attachments remain plaintext without setting either `MEMORY_SERVICE_ENCRYPTION_DB_DISABLED` or `MEMORY_SERVICE_ENCRYPTION_ATTACHMENTS_DISABLED`. Those scope-disable flags are overrides for real providers such as `dek`; `plain` must not advertise MSEH v4 field-encryption support because migration commands use that capability check.

**Runtime mode is not user-configurable**: `config.DefaultConfig()` uses `ModeProd`; tests and embedded test harnesses set `ModeTesting` programmatically. The serve CLI does not read `MEMORY_SERVICE_MODE`, so production hardening checks should key off `cfg.Mode` and must not document that environment variable as an escape hatch.
**Gin proxy trust default**: The pinned Gin `v1.12.0` `gin.New()` engine trusts all IPv4/IPv6 proxies until `SetTrustedProxies` is called. Main and management routers must explicitly call `SetTrustedProxies(nil)` when no validated proxy CIDRs are configured; do not rely on the library default.
**Universal proxy trust**: `MEMORY_SERVICE_TRUSTED_PROXY_CIDRS` intentionally accepts `0.0.0.0/0` and `::/0` as trust-all configurations for simple deployments. Keep the empty value as trust-none, reject malformed CIDRs, and document that universal trust lets direct callers select their forwarded client IP unless an external network boundary restricts access.
**Conversation channel naming**: The canonical agent-state conversation channel is `context` (OpenAPI string / gRPC enum `CONTEXT`); `/v1/memories` remains the separate episodic memory API surface.
**Conversation context API boundary**: Per-conversation `context` sync/list behavior lives under `/v1/conversations/:conversationId/entries` and `/entries/sync` plus the corresponding store methods in `internal/plugin/route/entries` and `MemoryStore`; `internal/plugin/route/memories` is only for the separate episodic `/v1/memories` APIs.
**Conversation ID type rule**: Conversation IDs are arbitrary non-empty strings across REST, gRPC, stores, caches, and vector payloads. Example apps may still generate UUID-shaped conversation IDs, but code must not parse/validate conversation IDs as UUIDs. Conversation group IDs remain `uuid.UUID`.
**REST path-parameter decoding**: Main and management Gin routers match `URL.EscapedPath()` with Gin unescaping disabled. Generated oapi-codegen wrappers perform the single RFC path unescape; `proxyAPIServer` / `proxyAdminServer` must copy each decoded wrapper argument back into `c.Params` before calling legacy route handlers that read `c.Param(...)`. Enabling Gin unescaping as well double-decodes `%25` values and corrupts literal percent-containing IDs.

**Go cache plugin architecture**: The Go service selects cache backends through `internal/registry/cache` and currently injects a `MemoryEntriesCache` into store loaders before datastore initialization. `cfg.CacheType` is shared by both the memory-entries cache plugins (`internal/plugin/cache/*`) and the response-recording locator-store selection in `internal/resumer/locator_store.go`, so new cache kinds usually need both an entries-cache implementation and locator-store behavior.

**GORM `record not found` log-noise rule**: If a `record not found` log line is found, treat expected-miss lookups as noise and refactor those call sites from `First(...).Error` to `Limit(1).Find(...)` with `RowsAffected` checks. Keep `First` for true not-found error paths; don't use global logger suppression.

**Error observability**: All 500-level errors MUST produce a full stack trace in the server logs. Never swallow exceptions silently — always log the stack trace for server errors.

**Embedded OPA Rego syntax**: Episodic policies compile with OPA's v1 Rego API. Use Rego v1 syntax (`if`, `in`) directly; do not add `future.keywords` imports to current policies.

**Default episodic policy and kind**: Built-in authz is deny-by-default and only allows `["user", <subject>, ...]` namespaces. The immutable built-in `default/v1` kind projects plaintext `{"namespace":"user","sub":<subject>}` into `policy_attributes`. Built-in filter injection scopes every public search/list caller to `["user", <subject>]`, even when that principal has an admin role; dedicated admin memory APIs bypass the filter except for `as_user_id`, which evaluates it as the target non-admin user.

**Episodic indexer pending rows**: `registry/episodic.PendingMemory.Namespace` is a single RS-delimited string (`\x1e`), not `[]string`; tests/mocks must provide encoded namespace values.

**Postgres append auto-create race**: Concurrent `AppendEntries` calls for the same missing conversation ID can race on root conversation/group creation and hit `23505` on `conversation_groups_pkey`. The append path must treat that unique-violation as a concurrent-create win, reload the conversation, and continue instead of returning 500.
**Postgres root-conversation upsert rule**: In `createConversationWithID`, root/start-from conversations must insert `conversation_groups` and `conversations` with `ON CONFLICT DO NOTHING` semantics. Catching `23505` after `Create(...)` is too late in Postgres because the surrounding transaction is already aborted and later reloads fail with `25P02`.
**Postgres duplicate-key diagnostics**: When conversation/group auto-create paths hit `23505`, the store now emits structured warning logs with `constraint`, `table`, and Postgres `detail` plus `userID`, `conversationID`, and `conversationGroupID` so CI flakes can be mapped back to scenario-specific IDs.
**oapi route registration gotcha**: Do not call generated `RegisterHandlers(...)` while other manual registrations for the same endpoints are mounted; Gin panics on duplicate `METHOD + PATH` registrations.
**Serve wrapper routing architecture**: `internal/cmd/serve/server.go` exposes Agent/Admin HTTP endpoints only through generated wrappers wired in `internal/cmd/serve/wrapper_routes.go`. Route packages expose handler methods used by those wrappers; do not reintroduce the legacy `MountRoutes` registration stack or proxy adapters.
**BuildServer metrics-before-validation rule**: `internal/cmd/serve.BuildServer` must initialize Prometheus metrics before `validateStartupConfig`; validation can call `recordUnsafeConfig`, and concurrent BDD scenario startup under `-race` otherwise reads `SecurityUnsafeConfig` while `InitMetrics` is still constructing it.
**Attachment disposition behavior**: User and admin direct download, download-url, and signed token endpoints accept `disposition=inline|attachment`; when omitted, routes do not set `Content-Disposition` so browsers choose from content type. S3 signed URLs must include disposition via `registry/attach.SignedURLOptions` at presign time, not by appending response header overrides after signing.
**Attachment browser-safety policy**: Attachment streaming always sets `X-Content-Type-Options: nosniff`. Active content types such as `text/html`, `application/xhtml+xml`, and `image/svg+xml` are served as `application/octet-stream` with `Content-Disposition: attachment` even if the caller asks for `inline`. S3 direct-download presigning is skipped for inline or active-content responses so the service can enforce those headers.
**History attachment reference normalization**: `internal/plugin/route/entries.resolveAttachmentRefs` preserves `attachmentId` in stored history content and does not populate `href`; for linked cross-entry/fork references it rewrites `attachmentId` to the newly created attachment record ID, then links that record to the new entry.
**Signed attachment download auth parity**: `/v1/attachments/download/:token/:filename` must remain unauthenticated (token-auth only). In wrapper mode, register this endpoint with a wrapper that has no auth middleware; otherwise BDD signed-download scenarios fail with 401.
**Encrypted attachment size sentinel**: Attachment backends treat `maxSize < 0` as "caller already enforced the logical plaintext limit". The encrypted attachment wrapper uses this to stream ciphertext without imposing an encrypted-size ceiling.
**MSEH formats**: Encrypted persisted fields accept only MSEH v4. Encrypted attachments accept only MSEH v3, a 64 KiB AES-GCM record stream with a 24-byte nonce (`8-byte key ID || 16-byte salt`). MSEH v1 field and v2 AES-CTR stream readers have been removed.
**Search wrapper-native migration**: `/v1/conversations/search`, `/v1/conversations/index`, and `/v1/conversations/unindexed` are bound through generated wrappers and handled directly via exported search route helpers (`internal/plugin/route/search/search.go`).
**Wrapper auth middleware gotcha**: Wrapper-native endpoints must run auth (and for memories, client-id) as wrapper middlewares in `internal/cmd/serve/wrapper_routes.go`; otherwise role checks can fail even when tokens are valid.
**Unix-socket listener validation**: Listener selection conflicts must use explicit flag/env detection (`cmd.IsSet(...)`), not non-zero resolved port values, otherwise the default port `8080` falsely conflicts with `--unix-socket`. When a Unix-socket parent directory is missing, the serve layer creates it as `0700`; if it already exists and is group/world accessible, startup must fail fast instead of chmod-ing it.
**TCP listener bind default**: Main and management TCP listeners default to `127.0.0.1`. Container, Kubernetes, and Fly deployments that expose the service through pod/container networking must set `MEMORY_SERVICE_HOST=0.0.0.0` and, for dedicated management probes, `MEMORY_SERVICE_MANAGEMENT_HOST=0.0.0.0` intentionally.

**Unix-socket local auth boundary**: `--unix-socket-auth=local` is valid only with an exclusive main UDS listener. It supplies the same configured local user/client identity to REST and gRPC without credentials; caller-provided `X-User-ID` / `x-user-id` assertions are intentionally ignored, so embedded clients that need a deterministic owner must set `--local-user-id`. Management listener selection does not broaden the API transport. Any process able to access the socket as its owning Unix user is inside this trust boundary.

**TLS self-signed certificate opt-in**: Omitting `MEMORY_SERVICE_TLS_CERT_FILE` and `MEMORY_SERVICE_TLS_KEY_FILE` only generates an ephemeral self-signed certificate when `MEMORY_SERVICE_TLS_SELF_SIGNED=true` / `--tls-self-signed` is set. Dev launch surfaces that enable TLS without cert files must set this explicitly.
**OIDC self-signed issuer opt-in**: `MEMORY_SERVICE_OIDC_TLS_INSECURE_SKIP_VERIFY=true` / `--oidc-tls-insecure-skip-verify` only affects outbound OIDC discovery and JWKS fetches in `internal/security/auth.go`; it does not change listener TLS or general HTTP client behavior.
**OIDC role/audience hardening**: OIDC always requires `MEMORY_SERVICE_OIDC_ALLOWED_AUDIENCES`; there is no issuer-only compatibility mode. Claim-derived roles come only from configured RFC 6901 JSON Pointer paths (`--oidc-role-claim` or `MEMORY_SERVICE_OIDC_ROLE_CLAIMS` JSON array), defaulting to `/realm_access/roles`; `scope`, top-level `roles`, and `groups` are not implicit role sources.

**gRPC recorder disconnect cleanup**: In `ResponseRecorderServer.Record`, if the stream fails with gRPC/ctx `CANCELED` or `DEADLINE_EXCEEDED` after a recorder has been created, call `recorder.Complete()` before returning so the locator/cache registry entry for that conversation is removed.

**gRPC cancel semantics**: `ResponseRecorderServer.Record` subscribes to `resumer.CancelStream(conversationID)` once the first chunk sets `conversation_id`; when cancel is requested it completes the recorder (removing locator/cache registry) and returns unary `RecordResponse{status=RECORD_STATUS_CANCELLED}`.
**Fork ancestry nil stop-point semantics**: In entry ancestry filtering (Postgres, SQLite, and Mongo), a nil `forkedAtEntryId` means "exclude all inherited entries from that ancestor and jump directly to the child conversation". This makes the first newly appended message the first visible entry in the fork.
**Conversation ancestry schema direction**: Enhancement 110 moves SQL fork lineage from persisted `conversations.forked_at_*` columns into `conversation_ancestry`; public/store response fields remain but SQL stores must hydrate them from the depth-1 ancestry row. Do not add new SQL reads or writes that depend on direct fork columns on `conversations`.
**Mongo conversation ancestry schema direction**: Mongo conversation documents no longer persist `forked_at_conversation_id` or `forked_at_entry_id`; `conversation_ancestry` stores one document per descendant with `parent_conversation_id`, `forked_at_entry_id`, and embedded ancestor rows. Mongo conversation summaries/details must hydrate fork metadata from that document.
**Mongo conversation publish order**: Mongo conversation creation claims `conversation_ancestry` first and inserts the conversation document last. Duplicate ancestry claims are accepted only when the requested lineage matches; matching orphan ancestry records may be deleted and retried.
**Conversation fork APIs**: user and admin `ListForks` return the complete group ID list plus fork points visible in the requested conversation. Direct lineage comes from SQL `conversation_ancestry.depth = 1` or Mongo `parent_conversation_id`.
**Current-state conversation snapshots**: event-stream snapshot pages hydrate direct fork and logical started-by metadata with page-wide datastore lookups. Do not call the single-conversation `hydrateConversationFork` helper inside the page loop; a 500-row bootstrap page must use a constant number of datastore operations.
**Event delivery JSON encoding**: gRPC and REST SSE delivery use `eventstream.MarshalDeliveryJSON` with HTML escaping disabled. Full resources may contain multi-megabyte strings dominated by `<`, `>`, or `&`; default `encoding/json` HTML escaping expands each byte sixfold and can exceed transport receive limits even when the stored resource is valid.
**ClickHouse entry payload boundary**: `indexedContent` is content-bearing plaintext and belongs only in generic `payload_json` under `full` mode, like entry `content`. Metadata and projected modes may retain the non-content `indexedAt` timestamp; projected output may use content only through explicitly approved projection fields.
**ClickHouse size limits**: `batch-bytes` is an aggregate flush target, not a per-record ceiling. `max-record-bytes` independently bounds one encoded record and determines the gRPC receive allowance with envelope headroom. Its default accounts for the twofold expansion of accepted U+2028/U+2029-heavy JSON during event serialization.
**BDD Mongo SQL-skip semantics**: `internal/bdd/steps_sql.go` treats `nil` rows as "skip SQL assertions"; `MongoTestDB.ExecSQL` intentionally returns `nil, nil`, so SQL verification steps in shared feature files do not validate datastore state on Mongo runs unless parallel Mongo-specific assertions are added.
**DB schema version 2 baseline**: PostgreSQL and SQLite are initialized from `internal/plugin/store/postgres/db/schema.sql` and `internal/plugin/store/sqlite/db/schema.sql`; Mongo initializes equivalent collections/indexes. Startup upgrades schema version 1 in place and rejects unknown or unversioned layouts for manual recovery.
**BDD Mongo query variable expansion**: Mongo query docstrings can contain Mongo `$` operators/field paths (for example `$ne`, `$match`, `$task_body.path`). Use brace-only expansion (`${var}`) for scenario variables; do not run generic `os.Expand` over whole Mongo query strings or `$ne`/`$foo` will be treated as missing variables.
**Godog report format switch**: BDD report writers honor `GODOG_REPORT_FORMAT`; default is `junit` (`.xml`), and setting `GODOG_REPORT_FORMAT=cucumber` writes Cucumber JSON (`.json`) under `GODOG_REPORT_DIR`.
**Cucumber report chunking tool**: `go run ./internal/cmd/create-cucumber-reports` scans `*/reports/*.json`, normalizes array/object report roots, and writes chunked combined files to `.artifacts/cucumber-report-###.json` (default max 50 features per file).
**BDD backend harness pattern**: Each datastore/backend gets its own `internal/bdd/cucumber_<backend>*.go` runner plus a matching `TestDB` implementation; shared feature files live under `internal/bdd/testdata/features*`, and backend-specific coverage is added with extra feature subdirectories instead of forking the whole suite.
**BDD gRPC event runner**: There is no standalone `TestFeaturesGrpc` runner. Common gRPC event scenarios under `internal/bdd/testdata/features-grpc/` run through `TestFeatures`, and the Postgres outbox runner includes `sse-events-grpc.feature` for outbox-enabled gRPC coverage.
**BDD rate-limit isolation**: `defaultBDDConfig()` disables process-local rate limiting so functional BDD runs are not order/load sensitive; rate-limit behavior belongs in focused tests with intentionally low limits, such as `internal/security/rate_limit_test.go`, or a dedicated BDD runner if end-to-end rate-limit scenarios are added.
**Rate-limit operational diagnostics**: Local HTTP 429 and gRPC `ResourceExhausted` rejections add `rateLimiter` to the canonical operational event. Values match the metric classes: `source`, `identity`, `auth_failure`, `expensive`, and `stream_open`.
**`internal/bdd` isolation strategy**: general user-scoped runners still use `bddScenarioConcurrency()`. All SQLite BDD runners provision a dedicated memory-service server plus SQLite file per scenario, while the common serial PostgreSQL and Mongo runners keep one shared server/datastore instance and run serial-only common features with `Concurrency = 1`.
**BDD scenario identity isolation**: `internal/testutil/cucumber` gives each `internal/bdd` scenario a short suffix for both canonical test users and agent `clientId`s. The harness rewrites known user IDs through request paths/bodies, gRPC prototext, and JSON/text responses, and it suffixes `X-Client-ID` values in `I am authenticated as agent with API key ...` so shared caches and client-scoped context entries do not collide across concurrent scenarios.
**BDD API-key wording gotcha**: The common non-OIDC BDD step `I am authenticated as agent with API key ...` uses `auth_testfixtures` + `ModeTesting` `X-Client-ID` identity, not production `X-API-Key` validation against `MEMORY_SERVICE_API_KEYS_<CLIENT_ID>`. Add focused production-mode auth tests when real API-key header behavior matters.
**gRPC BDD UUID field gotcha**: `conversation_id` is a proto `string`; interpolate `${conversationId}` directly in textproto. Only UUID-valued `bytes` fields need `uuid_to_hex_string`, and `steps_grpc.go` injects that transform automatically for unfiltered UUID variables.
**BDD table parsing gotcha**: `godog.Table.Rows` includes the header row used in feature files. Step parsers that expect data rows must explicitly skip headers such as `| role | scope |`.
**BDD role-user config**: non-OIDC BDD runners configure static role users with wildcard suffixes like `alice-*` / `dave-*`, and the auth layer plus gRPC search-role checks honor `*` suffix prefix matches. That lets isolated subjects such as `alice-1a2b3c4d` keep admin/auditor/indexer roles inside concurrent scenarios.
**BDD ordinary-user isolation tests**: In `internal/bdd`, `alice` is admin, `charlie` is auditor, and `dave` is indexer (including isolated `*-<suffix>` subjects). Use users such as `bob` and `erin` when a scenario must prove ordinary user-to-user isolation.
**Mongo attachment storage**: Mongo GridFS attachment storage is intentionally unsupported because the Go driver upload path is unsafe under concurrent use. Mongo deployments must use S3 or filesystem attachment storage; filesystem storage requires an explicit attachment directory.
**BDD OIDC user provisioning**: `internal/testutil/testkeycloak` provisions scenario-local OIDC users on demand through the Keycloak admin API, and `deploy/keycloak/memory-service-realm.json` grants the seeded `alice` test user `realm-management` `realm-admin` so those provisioning calls can run over the imported test realm.
**S3 testcontainer image pinning**: `internal/testutil/tests3` should use an immutable `localstack/localstack@sha256:...` image reference, not `:latest`; Localstack `latest` can change under CI and fail during startup before the S3 BDD runner even creates the bucket.
**CGO SQLite runtime**: Runtime build paths now use `CGO_ENABLED=1` with `sqlite_fts5 sqlite_json` in both the repo `Dockerfile` and `deploy/dev/air.toml`. Any new SQLite-specific runtime code should assume CGO is available in dev and container builds.
**SQLite container base image**: The production `Dockerfile` must stay on a glibc-based image (currently UBI 9), not Alpine/musl. `sqlite-vec` needs SQLite development headers and fails to compile cleanly against musl in the multi-arch container build used by CI.
**Portable Linux binary image**: `Dockerfile.portable` is intentionally separate from the production UBI image. It builds a static musl Linux binary with SQLite, FTS5, JSON, and sqlite-vec enabled, using `sqlite-dev` for headers and `CGO_CFLAGS="-Du_int8_t=uint8_t -Du_int16_t=uint16_t -Du_int64_t=uint64_t"` to work around sqlite-vec v0.1.6's BSD typedef assumptions on musl.
**Runtime version source**: Docker builds set `main.Version` with `-ldflags "-X main.Version=<version>"`; release builds pass the release version, and main-branch CI builds pass `github.sha` for the `latest` image. `main` passes that value into `internal/runtimeversion`, which is used by capabilities, the `version` subcommand, and the turn-traces processor. Do not reintroduce `MEMORY_SERVICE_VERSION` as a separate runtime-version source.
**REST tx-scope helper**: Route handlers that need `MemoryStore` or `EpisodicStore` transaction intent should use `internal/plugin/route/routetx` so the transaction-scoped context is attached to Gin’s request context before downstream store calls.
**Direct episodic fetches are write-scoped**: `GET /v1/memories` must use `EpisodicStore.InWriteTx`, not read scope, because the handler increments usage counters in the same workflow.
**Episodic archive parity**: Memory APIs now follow the same archive model as conversations. `GET /v1/memories`, `POST /v1/memories/search`, and `GET /v1/memories/namespaces` accept `archived=exclude|include|only`, archived memories remain directly readable, and the current memory state is the latest row per `(namespace,key)` rather than only rows with `archived_at IS NULL`.
**Episodic search filter injection gotcha**: Current `PolicyEngine.InjectFilter` merges caller and OPA `attribute_filter` values into a plain map, so same-key constraints are overwritten. Enhanced search work needs a normalized/conjoined filter representation before adding richer operators.
**Episodic event semantics**: Memory archive operations are represented as `update` lifecycle events at `archived_at`; `ListMemoryEvents` no longer exposes a `delete` kind for archive PATCHes.
**Episodic semantic search archive behavior**: Semantic `/v1/memories/search` honors `archived=exclude|include|only` too. Archived memory vectors are retained for manual archive (`deleted_reason=1`), vector backends filter by archive state before ranking, and hydrated results are post-filtered against the memory rows for correctness.
**Background store workers are tx-scoped**: `BackgroundIndexer`, `TaskProcessor`, `EvictionService`, `AttachmentCleanupService`, `EpisodicIndexer`, and `EpisodicTTLService` now declare store read/write intent via `InReadTx` / `InWriteTx` instead of calling store methods on an unscoped context.
**SQLite conversation vector backend**: `internal/plugin/vector/sqlitevec` uses a regular `entry_embeddings` table plus `sqlite-vec` scalar distance functions, not a separate `vec0` virtual table. That keeps schema/migrations simple and works with the shared GORM SQLite handle.
**SQLite episodic vector backend**: `internal/plugin/store/sqlite/episodic_store.go` stores episodic `memory_vectors.embedding` as serialized float32 BLOBs and queries them with `vec_distance_cosine(...)` plus SQLite JSON1 filters, mirroring the conversation-side `sqlite-vec` scalar-function approach.
**SQLite shared handle policy**: `internal/plugin/store/sqlite/shared.go` augments every SQLite DSN with `_foreign_keys=1`, `_journal_mode=WAL`, `_busy_timeout=5000`, and `_synchronous=NORMAL`, then uses a small multi-connection pool (`8` open / `4` idle). The shared handle is still process-wide; this avoids deadlocking request-scoped store transactions against vector-store local transactions on a single physical connection.
**SQLite startup fallback**: `internal/plugin/store/sqlite` now creates parent directories for file-backed DB paths before opening SQLite and probes both FTS5 and `sqlite-vec` support on the shared handle. When either extension is unavailable, migrations skip the corresponding optional schema and search/index paths degrade to empty/no-op behavior instead of failing startup.
**Infinispan vector-store split**: `internal/plugin/vector/infinispan` is a separate REST API v3 integration, not the RESP-backed cache/event-bus path. It needs Infinispan `16.1+`, defaults to `MEMORY_SERVICE_VECTOR_INFINISPAN_URL=http://localhost:11222`, and only falls back to the shared `MEMORY_SERVICE_INFINISPAN_URL/USERNAME/PASSWORD` values for connection reuse.
**gRPC tx-scope parity**: `internal/grpc/server.go` now declares `InReadTx` / `InWriteTx` around `MemoryStore` and `EpisodicStore` calls so the SQLite datastore can be registered globally without unscoped gRPC access paths.
**Episodic memory CAS**: gRPC and REST `PutMemory` / `UpdateMemory` support `expected_revision`; stores persist a monotonic per-`(namespace,key)` `revision` on each memory version and return `ErrMemoryRevisionConflict` as gRPC `ABORTED` or REST `409`.
**Episodic Put predecessor CAS**: User Put authorization captures the active row ID/revision (including explicit absence) and passes it to `PutMemory`. Stores archive only that predecessor and return `ErrMemoryRevisionConflict` if active state changed; a unique partial active-row index enforces one active `(namespace,key)` row.
**Episodic schema baseline**: Core datastore schema version 2 upgrades populated version-1 PostgreSQL, SQLite, and MongoDB layouts in place, backfills memories to `default/v1`, and invalidates/deletes derived vectors for repair before advancing version metadata.
**Trusted client user assertion**: Normal user REST calls may use `X-User-ID` and gRPC calls may use `x-user-id` metadata only when the authenticated client ID is in `MEMORY_SERVICE_TRUSTED_USER_ID_CLIENTS`. Untrusted assertions are ignored. Admin/system APIs ignore assertions. Protobuf requests contain no `RequestActor`; effective identity is established at the transport boundary before authorization and identity rate limiting.
**Admin episodic memory writes**: Admin REST/gRPC memory write/update APIs are authorized by admin role/scope/justification and bypass episodic OPA authz. Admin puts use the selected immutable memory-kind projection with persisted namespace/key/value/index inputs; no caller context participates in projection.
**Admin episodic memory REST guard**: New `/admin/v1/memories` write handlers must call `ensureAdmin` in the handler, not rely only on generated proxy permission/scope checks; non-OIDC fixture users can otherwise reach admin memory writes when no OIDC scope gate is configured.
**Admin memory BDD runner**: `admin-memories-rest.feature` and `admin-memories-grpc.feature` use raw bearer admin/user fixture auth and therefore run under `TestFeaturesAuthFixturesSQLite` with the `auth_testfixtures` build tag, not under the broad default runners.
**Event-stream payload parity**: Membership event notifications use `data.user` across REST SSE and gRPC stream consumers. Conversation `deleted` notifications come from hard-delete paths (for example eviction), not archive PATCHes, and must carry a pre-captured `members` list because membership lookups are empty after the delete transaction commits.
**Event-stream normalization for 090**: REST SSE and gRPC event contracts now reserve `after` / `detail` replay parameters and use normalized business action names (`created`, `updated`, `deleted`) instead of legacy action-specific verbs such as `appended`, `added`, or `removed`. Entry and response event payloads must include `data.conversation_group`.
**Postgres outbox relay**: PostgreSQL outbox replay now uses opaque numeric `event_seq` cursors assigned by the `pgoutput` logical-decoding relay. `AppendOutboxEvents(...)` only persists rows (`event_seq` starts `NULL`), request-path `eventstream.PublishEvents(...)` is suppressed when Postgres outbox replay is enabled, and a single advisory-lock leader batches `event_seq` materialization per committed transaction before republishing the durable business event.
**Postgres outbox relay startup logging**: Initial relay bootstrap errors are returned to `serve.StartServer(...)` and should not also emit `Postgres outbox relay stopped` warnings; keep WARN logs for post-start background failures only.
**Postgres outbox relay shutdown noise**: `internal/plugin/store/postgres/outbox_relay.go` treats shutdown-time reconnect errors (`context canceled`, `connection refused`, `unexpected EOF`, closed network connection) as normal exit conditions. Keep those suppressed so testcontainer teardown does not emit misleading relay warnings.
**Postgres test harness replication**: `internal/testutil/testpg.StartPostgres` starts the PG18 test container with `wal_level=logical`, `max_replication_slots`, and `max_wal_senders` set so Postgres outbox relay tests can create a logical replication slot/publication without extra bootstrap.
**Postgres BDD task timestamps**: `PostgresTestDB` task helpers use Go-side UTC timestamps for `created_at` / `retry_at` and ready-task comparisons. Do not mix database `NOW()` with Go-side assertions, because testcontainer clock skew can make retry scheduling checks flaky.

**Response event detail mode**: `response` events intentionally keep the same compact payload as `detail=summary` on REST SSE, admin SSE, and gRPC streams. Full detail enriches conversation and entry events; privileged admin REST and gRPC streams also enrich memory events when the memory still exists.
**gRPC full event payload shape**: `EventStreamService.SubscribeEvents` always carries JSON bytes in `EventNotification.data`; `detail=full` swaps in marshaled internal `model.Entry`, `ConversationDetail`, or admin `MemoryItem` JSON for supported events, not generated proto resource messages. Full-detail enrichment preserves the original summary `conversation_group` as `conversationGroupId` for processor correlation, while internal struct fields like `ClientID` that remain `json:"-"` are still omitted.
**Full event/OpenAPI mismatch**: `detail=full` currently marshals internal resource structs instead of using REST response converters. Conversation events expose `archivedAt` instead of OpenAPI's synthetic `archived` and admin events omit `clientId`; memory events expose `memoryKind` instead of required `kind` and omit `archived`; entry events include internal fields absent from the documented `Entry` schema. Treat this as a contract gap when changing full-event consumers.

**Mongo outbox relay**: With outbox enabled, `MongoStore.InWriteTx` uses a real `mongo.Session` transaction and startup requires a replica set or mongos. Public cursors are opaque `mongo:<base64url BSON>` values: live rows use change-stream tokens and recovered rows use stable relay-generated anchors. **ClickHouse schema baseline**: The analytics exporter starts at schema V1. V2, V3, and V4 were unreleased development drafts; reset development ClickHouse databases created from them rather than adding compatibility code. **ClickHouse tombstone retention**: Payload-free deletion fences outlive row TTLs and suppress generic, typed, and projection current rows whose ingest version is not newer than the latest deletion. Schema V1 installs a materialized view that mirrors every generic tombstone into the fence table. Duplicate fence rows are safe under the table's replacing key and max-version view. This prevents physical TTL merge order from resurrecting old rows. Positive tombstone retention still requires positive active-row retention no greater than the tombstone duration to limit how long old physical payload rows remain.
**ClickHouse compliance purge correlation**: Projection rows, projection failures, deletion fences, and retry subject records persist only the payload-free source identifiers needed for purge. A hard delete durably records resolved dependent IDs before mutation, deletes dependent data before its discovery sources, removes fences last, deletes retry subjects, and then records completion. The processor validates and enumerates the projection registry so removed historical projections receive fence-aware views, retention, and purge. Schema V1 includes the required correlation fields from the start.
**ClickHouse stream invalidation and retention ownership**: A `stream/invalidate` marker stops the exporter with a `backfill_required` error without flushing pending work, clearing the durable cursor, or running a current-state bootstrap; recovery requires a complete backfill that can reconcile resources deleted during the missing history. Retention settings are database-wide while exporters are active: each sink registers a heartbeating owner with a 30-second liveness window, matching live owners may coexist, conflicting live owners are rejected before TTL changes, and stopped or expired owners permit a later policy update. Before every batch write, the sink verifies that its existing owner is still live, renews it, and revalidates the shared policy. Expiry, renewal failure, or conflicting takeover reports a terminal background error, makes the process unready, and stops the runtime before it writes the batch. Schema `validate` mode still registers this owner using DML, but never applies schema or TTL DDL.
**Processor lease loss**: The shared process runtime uses a lease-scoped work context. Renewal failure cancels in-flight bootstrap, event handling, flush, and checkpoint work, and skips the graceful shutdown flush before returning the lease error.
**ClickHouse analytics transport bounds**: Processor gRPC clients accept responses through 9 MiB, covering the server's 8 MiB analytics response contract. Backfill halves its page size and retries the same page token on `ResourceExhausted`; a failure at page size 1 is terminal.

Migration source must exist in the datastore with at least one matching row; no legacy runtime special-case applies.

**Nested metadata no-op comparison**: MongoDB can decode nested metadata objects and arrays as BSON ordered-document/array types while REST, gRPC, and SQL paths use ordinary Go maps and slices. `MetadataPatch.ChangesAgainst` must compare these as JSON-semantic values, including bounded exact numeric normalization, rather than with `reflect.DeepEqual`, or identical retry patches update `updated_at` and emit duplicate conversation events.

**Archived sequenced retry insertion**: For a validated append carrying `conversationPatch.archived=false`, handlers use `AppendEntriesBeforeUnarchive` to attempt insertion while the conversation remains archived. A new entry is followed by unarchive; a duplicate is compared while still archived and only an exact retry completes the unarchive. Mismatches therefore leave archive state and retention timestamps untouched. Ordinary `AppendEntries` and `SyncAgentEntry` continue rejecting archived conversations.

**Append-time archive transition accounting**: Retry-capable append paths use `ArchiveConversationIfNeeded` / `UnarchiveConversationIfNeeded`, whose `Changed` result identifies the caller that performed the transition. Already-satisfied state is a successful no-op, allowing the original entry inserter to finish attachment linking and entry event creation after an identical concurrent retry wins the archive transition; only the transition winner emits the archive update.

**Sequenced retry attachment repair**: Exact single-entry retry recovery must repair direct history `content[*].attachments[*]` links from the stored entry before returning success. This completes a Mongo append that persisted the entry and cloned attachment but failed before linking; retry-created temporary clones are cleaned separately and must never be confused with stored referenced attachments.

**ClickHouse analytics export (Enhancement 404)**: `memory-service process clickhouse` exports PostgreSQL, SQLite, and MongoDB durable events into lifecycle, generic resource, and typed projection tables. It uses a renewable CAS lease and generation-fenced ingest versions, runs restartable high-water/backfill/catch-up bootstrap, supports metadata/projected/full payload boundaries, evaluates immutable deployment-owned Rego projections, and performs durable hard-delete purges. Cross-table writes are not transactional: the checkpoint advances only after every table write succeeds, while partial writes remain visible and replay plus stable event/resource keys provides logical idempotency. Compose enables projected mode with the bundled example-app projections; both top-level Kustomize overlays enable metadata mode. `--projection-path` accepts a file or directory; a directory loads its direct `*.yaml` and `*.yml` files, ignores other resource kinds, and does not recurse. The bundled `history`, `history/lc4j`, and `history/vercelai` projections store typed role, text, event, tool, and attachment analytics without retaining raw history content JSON. The bundled `SpringAI` projection stores ordered role/text arrays and per-role message counts without raw content JSON. Schema `validate` mode compares the configured retention policy with TTL expressions in `system.tables` for lifecycle, generic resource, projection-failure, and every registered projection table before registering the live retention owner; it never applies TTL DDL. Processor-owned ClickHouse relations use concise names inside the configured database rather than repeating a `memory_service_` prefix. Projection `metadata.name` is the exact physical table name; processor-owned relation names and the `_current`/`_all` suffixes are reserved. Projection columns support portable types plus ClickHouse-specific tagged `Variant` and bounded native `JSON`; exporter-owned tables remain on portable types.

**ClickHouse output selectors**: `--disable` / `MEMORY_SERVICE_CLICKHOUSE_DISABLE` accepts `RESOURCE`, `RESOURCE:FEATURE`, and `*:FEATURE`. Resources are `conversations`, `entries`, and `memories`; features are `lifecycle_events`, `lineage`, and `projections`. Invalid resource-feature pairs fail validation. The checkpoint stores enabled outputs. Re-enabling lifecycle, lineage, or a full resource requires a reset or new exporter ID; projections require a new replay ID. Disabled configured projections are parsed but are not created or populated. Managed and record-only purge keep all resource event kinds subscribed so hard deletes can remove rows written before an output was disabled; external purge subscribes only to enabled resources.

**ClickHouse data lifecycle ownership**: `--retention-mode=external` bypasses retention ownership, TTL validation, and TTL DDL, and requires all processor TTL durations to be zero. `--purge-mode` supports `managed`, `record-only`, and `external`; record-only writes pending purge requests without executing mutations, while external emits no purge request. Moving a checkpoint from record-only or external back to managed is rejected because earlier hard deletes may have been skipped. `deletion_fences` remain active in every mode because processor-owned current views depend on them.

**History entry shape**: The REST write validator requires a history-channel entry's `content` array to contain exactly one object with at least one of `text`, `events`, or `attachments`. `role` is optional at runtime; when present it accepts `USER`, `AI`, or `SYSTEM`, although current OpenAPI prose describes it as required and lists only `USER` and `AI`.
**ClickHouse source-lag limitation**: `memory_service_clickhouse_processor_source_lag_seconds` measures the age of the most recently accepted source event. It grows when the source is idle and does not compare the saved processor cursor with the datastore's current outbox high-water cursor. ClickHouse can calculate delivery delay for received lifecycle rows, but it cannot prove that the processor has caught up without a separate high-water comparison.
**ClickHouse password configuration**: The analytics processor accepts a direct password only through `MEMORY_SERVICE_CLICKHOUSE_PASSWORD`; `--clickhouse-password-file` / `MEMORY_SERVICE_CLICKHOUSE_PASSWORD_FILE` remains available for mounted secrets. Configuring both forms is an error.

**ClickHouse identity export**: Analytics rows store source Memory Service identifiers in `String` columns so query results can resolve authoritative resources through the Memory Service API. The exporter does not transform identifiers or version their representation.

**ClickHouse entry event fields**: Durable entry summaries use the event-stream metadata keys `entry_content_type`, `entry_channel`, and `entry_role`. ClickHouse lifecycle routing consumes those keys. Full events carry the scope-appropriate OpenAPI Entry JSON in `data`, including `contentType`.
**ClickHouse entry subscription channels**: Event streams default to the `history` entry channel when `entry_channels` is empty. The ClickHouse processor must explicitly subscribe to `history`, `context`, and `journal` during current-state initialization and normal replay/live processing, or context projections such as LC4J and Spring AI silently miss rows.

**ClickHouse lineage query shape**: `conversation_lineage_current` currently uses the generic resource schema and stores only direct parent-to-child edges. Read `ancestorConversationId`, `descendantConversationId`, `depth` (always `1`), and optional `forkedAtEntryId` from `payload_json`; they are not yet physical columns despite the Enhancement 404 schema description. ClickHouse subscribes with admin scope and `detail=full`. Full conversation resources carry optional direct-fork fields during current-state initialization, replay, and live delivery. Roots have no ClickHouse lineage row; derive transitive ancestry recursively.
**Full event resource contract**: `detail=full` replaces summary `data` with the exact scope-appropriate OpenAPI resource JSON. Agent streams use agent resources; admin streams add output-only internal fields such as `clientId` and `conversationGroupId`. The envelope preserves the summary lifecycle marker in top-level `change`. Admin `initial_state=current` requires `detail=full`, a replayable outbox, and no caller cursor; it emits snapshot resources behind a high-water boundary before replay and live phases. The ClickHouse processor filters full resources according to its payload mode; metadata allowlists control ClickHouse storage, not the data sent to the processor.
